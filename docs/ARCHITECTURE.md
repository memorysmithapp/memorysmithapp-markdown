# Architecture

How `memorysmithapp-markdown` is organised, and why: what it is made of, what enforces each invariant of [`AGENTS.md` §5](../AGENTS.md#5-invariants), what it integrates with, and the decisions behind it.

Claims carry their status when it is not obvious: *observed*, *declared*, *inferred*, and **To confirm** for what was not verified.

## 1. Overview

*Instruction: what the system is made of, and how the parts relate.*

The repository is made of:

- **Documents**, the core of what it delivers: `.claude/CLAUDE.md` imports `AGENTS.md`; `AGENTS.md` maps the reading and the writing onto `PRD.md`, `ARCHITECTURE.md` and `SDLC.md`, which live in `docs/`, and `README.md`, and states the limits and invariants in one line each; `CHANGELOG.md` records what each version changed. The root holds only what a tool or a convention looks for there ([ADR-007](#adr-007-the-root-holds-only-what-a-tool-looks-for-there)).
- **Two packages**, in a pnpm workspace under `packages/`: `@memorysmithapp/markdown-spec` and `@memorysmithapp/markdown-renderer`, each built with TypeScript into its own `dist/` and tested with Vitest.
- **Two demonstration notebooks**, `notebooks/continuity-engineering` (en-US) and `notebooks/enologia` (pt-BR), written in MemorySmith's repository so that every declared notation appears in context; they are fixtures of the tests and documentation for a person. Beside them, `notebooks/code-samples` (en-US) holds one note per language highlighted on the first paint and four whose grammar is fetched when used (#84); it demonstrates no notation, and is drawn, compared and opened in the editor like the others.
- **A playground**, `playground/`, a private Vite page of the workspace that draws any note of the notebooks with the renderer, under an in-memory host, in the default theme, light and dark, and in three example themes, and edits any of them beside the bytes it would save; it is how a person looks at the renderer and the editor.
- **Repository files:** `package.json`, the one home of the version and the root of the workspace; `.gitignore`, `.editorconfig` and `LICENSE`.
- **A setup script**, `scripts/setup-repo.sh`, which applies to a repository the GitHub configuration a copy does not carry, and puts it back when it drifts.
- **A quality workflow**, `.github/workflows/quality.yml`, which runs `scripts/quality.mjs`, builds and type-checks the packages and runs every test on every pull request and push to `main`; the ruleset requires it.
- **A release workflow**, `.github/workflows/release.yml`, which tags and publishes a version once its bump is merged.
- **GitHub configuration**: the ruleset `main` and the settings the script applies.

### 1.1 The renderer

`@memorysmithapp/markdown-renderer` exports one component, **`NoteBody`**, which draws the body of a note. The name says what it draws — the body, never the frontmatter, which a host shows as properties — and leaves `Markdown` to the component that draws one parsed run, as MemorySmith's reading page names it.

- **`NoteBody`** (`src/NoteBody.tsx`) takes the note as the host keeps it, frontmatter included, and draws it inside `<div class="markdown">`: first the frontmatter, read by `readProperties` (`src/properties.ts`) and drawn by `Properties` (`src/PropertiesBlock.tsx`) as the theme decides ([§1.3](#13-themes)), then the body. It is MemorySmith's `WritableContent`: it splits the body into runs of text and embeds (`splitEmbeds`, `src/embeds.ts`), resolves the wikilinks of each run, and draws each run with `Markdown` and each embed with `Transclusion` — the body of the one note a target reaches, asked of the host's `loadNote`, cut to the section or block its anchor names, its own embeds demoted to links so the page expands one level only, and the note it came from named in a caption. Past `EMBED_LIMIT` (10) embeds, and inside a table cell or code, an embed is a link, never dropped. A footnote is resolved inside one parse, so when an embed cuts the note `planFootnotes` (`src/footnotes.ts`) reads the runs through the same remark plugins, with `unified` and `remark-parse`, and plans them as one document: each run is handed the top-level definitions of the other runs after its own text, which moves no offset a task box counts from; `rehypeFootnoteRun` drops each run's own section and gives each reference the number and the id the note gives it; and one more `Markdown` pass, `rehypeFootnoteSection`, draws the note's one section at its end from every reference in order and every definition. A note no embed cuts, with no definition, or with one inside a quote or a list, is drawn as before. An in-page anchor looks for its target in the whole note, outside any embed, so a way back reaches a reference in another run; inside an embed it looks in the embed.
- **`Markdown`** (`src/Markdown.tsx`) is MemorySmith's `Markdown` component: `react-markdown` over the text with newlines normalised, no raw HTML (no `rehype-raw`), `followable` as `urlTransform`, the footnote labels of the host, and the components that draw an anchor and an image. Its plugins, `readingPlugins` (`src/reading.ts`, a module with no React, which `planFootnotes` and `diagnose` read through too), run in this order, and the order is part of the contract:
  1. `remark-gfm`, at `singleTilde: false`, so `H~2~O` is not struck;
  2. `remarkParameters` (`src/parameters.ts`), **first** of the transforms, because it reads the position the parser gave each text node and the transforms after it build nodes with none: a text node whose source writes a parameter reference (`SPEC.md` §7.14) is cut into text and `parameter` nodes, drawn as `<span class="parameter" data-parameter="…">` holding the characters as typed and titled by `strings.parameter`. Escapes are gone from the value, so the references are found on the source by `parameterReferences` — a `{{` after an odd run of backslashes is text — and each piece between them is decoded as the parser decoded it, by `micromark-util-decode-string` with the continuation lines' container prefixes and the spaces before a soft break taken off; a node whose pieces do not add up to its value is left whole, so a reference may go undrawn but text is never drawn wrong. Code, math, raw HTML and destinations are not text nodes, and a link whose source does not open with `[` is an autolink, whose text is skipped;
  3. `remarkCallouts` (`src/remark-callouts.ts`), titled by `strings.callouts`, or by the kind capitalised;
  4. `remarkHighlight` and `remarkBlockIds` (`src/remark-ring.ts`), on text nodes only, so nothing inside code is touched; `remarkHighlight` reads a run of text and parameter nodes as the one text it was written as, so `=={{name}}==` marks the parameter;
  5. `remark-math`;
  6. `remarkMathDollarRule`, **after** `remark-math`: it gives back to the text an inline formula that breaks the dollar rule of `SPEC.md` §7.8, reading the source the parser read, so `R$100 e o frete R$200` stays a sentence;
  7. `rehype-katex` with `throwOnError: false`, so a formula KaTeX cannot typeset shows its source.

  A task item is drawn by `TaskItem`, which reads its state from the `input` GFM produced — react-markdown hands a component the hast element, which has no `checked` of its own — and reports the ordinal of its box: its position in the run, mapped by `ordinalAt` (`src/tasklist.ts`) to the n-th box of the run's text, plus the boxes of the runs and the frontmatter above it. The boxes are enabled only when the host made the note `writable`, and only when the boxes of the source and of the resolved runs agree in number, because `- [[x]]` resolves to `- [x](…)`, which GFM reads as a box the source does not have. Boxes are counted after any block quote markers, so a box inside a callout has an ordinal of its own, and never inside a fence or a comment, on the side the page draws and on the side `toggleTaskAt` writes alike.

  Before the parser, `NoteBody` rewrites the text it hands it, never the note. First `hideComments` (`src/source.ts`) takes out every comment (`SPEC.md` §7.6): from a `%%` outside code to the next one, across markup and blank lines, with the line break after it when the comment is all of its lines, so nothing a comment holds is parsed, expanded or linked, and no empty line is left to loosen a list; `Transclusion` does the same to the note it embeds. MemorySmith's reading page hides a comment inside one run of text only (RN-RENDER-012). Then `resolveWikilinks` (`src/source.ts`) turns each `[[name]]` outside code into a Markdown link to the host's address, to `pending:` when no note answers, to `choice:` when the host has `choose` and no single note answers, to `parameter:` when the target writes a parameter reference, which no note answers yet and which is not pending (`SPEC.md` §5.2), and each `![[file]]` the host `keeps` into `attachment:` with its dimension; `splitEmbeds` leaves an embed of a parameter in its run, demoted to that link. Code — fences by the specification's rules, code spans by their runs — is found before anything is rewritten, so notation inside it stays characters. The anchor of the surface turns each of those schemes into what it is: `parameter:` into a `.wikilink-parameter` span titled by `strings.parameterLink`, around the parameter its label draws, `pending:` into a pending span, `attachment:` into the host's `renderAttachment`, `choice:` into `LinkChoice`, a modal dialog of the notes the host's `choose` answers. `followable` lets the four schemes through. An image is drawn by `MarkdownImage`, which asks `keptImageName` (`src/kept-image.ts`, no React) whether its destination names a kept file — no scheme and no leading `//`, the last segment of its path, `/` and `\` separating, its query and fragment dropped, percent-decoded leniently and in NFC (`SPEC.md` §5.8, #104) — and draws that name through the same `Attachment` as an embed, handing it the description and the title the image wrote; a destination that names a host is an `img` of its address, as before. Either way the description is the image's `title` too, the hover hint, unless a title was written (#109). The editor draws its images with `MarkdownImage` too, so neither mode asks a path under the page for a picture.

  Code is drawn by three branches, in this order: a `mermaid` fence reaches `MermaidDiagram` untouched; a fence whose language `refractor` carries is tokenised into a hast tree that `hast-util-to-jsx-runtime` turns into React elements, never an HTML string — `src/highlight.ts` registers MemorySmith's fifteen grammars at once, and `src/prism-grammars.ts`, which `scripts/prism-grammars.mjs` writes from the installed `refractor`, lists every other one of its 297 with its aliases, the name a person reads and the dynamic import that loads it, which `MarkdownCode` calls the first time a fence names it, drawing the block plain until it arrives and highlighted after (#84); everything else is drawn as it was typed. A fence other than a diagram sits in a `.code-block` frame with a `CopyButton` that copies the `textContent` of the code less the newline before the closing fence.
- **`diagnose`** (`src/diagnose.ts`), exported at `@memorysmithapp/markdown-renderer/diagnose`, reports the notices of a note (`SPEC.md` §7.13) and draws nothing. It reads the note as `NoteBody` does — the frontmatter cut by `bodyStart`, the comments taken out by `hideComments`, whose map gives each position back in the note as written, the body parsed by `remark-parse` through `readingPlugins` — and keeps a copy of the tree as the parser left it, because the plugin that cuts a run of text for marked text drops the positions of what it cuts. From the transformed tree it takes what has a node: a fence or a `$$` block whose last line, its container's markers taken off, does not close it; a formula KaTeX refuses with `throwOnError` (and `strict: 'ignore'`, so it never writes to the console); a `mermaid` fence, read by `mermaid.parse` through `import('mermaid')`, only when a note holds one and `diagrams` is not `false`; raw HTML; a footnote definition no reference reaches; and the headings at the top level of the body. From the parser's text nodes it takes what stays characters: `[^label]` left as text, and a run between single tildes. The frontmatter is read by `readProperties`, with each key's line found by the same key pattern. Pending links are read on the body outside code with the pattern `resolveWikilinks` uses, and only when the host gives `resolve` or `reaches`; an embed is answered by a note or by `keeps`, and an image node whose destination `keptImageName` reads as a kept file's name by `keeps` alone, raising `embed-pending` when nothing is kept under it (#104). Each notice carries its code, the severity and section of `NOTICES` — the table of §7.13, held equal to `spec.json` by a test — an English message, and its start and end as lines and columns of the whole note. With no DOM, Mermaid fails on the sanitiser when it reads a label of some diagrams; only a parse error or an unknown diagram type is a notice, so a diagram it could not finish reading on a server raises none rather than a false one. A fence whose info string is the word `table` is read by `readTableBlock` and checked by `checkTableBlock` against the table the host's `tables` answers for its name, each mistake placed on the line of its key, counted from the fence's own line (#137).
- **The `table` block** (`src/table-block.ts`, no React and no DOM) reads a block's lines into its six keys (`SPEC.md` §7.15) and its `where` into a tree, and says what is wrong with it: alone, as `readTableBlock`, and against a table's columns, as `checkTableBlock`, one mistake a line, the ones of a key's syntax before the ones of its columns. The query language (`SPEC.md` §6.9) is a port of MemorySmith's `SearchQuery.ts` at `4b67c7e`: the same tokenizer, the same precedence and the same folding, with a range kept as its two ends until the kind of its column says whether they are inverted, and a phrase read as text whatever it holds ([ADR-008](#adr-008-the-query-language-is-read-here-ported-from-memorysmiths-search)). `runTableQuery` answers a request from rows held in memory as §6.9 and §7.15 say: the filter by the kinds of the columns, the order with an empty value last and ties in insertion order, the page, and the total summed exactly as decimals in `bigint`, never through a floating point; the playground answers with it.
- **`DataTable`** (`src/DataTable.tsx`) draws a `table` block where the host gives `queryTable` (#138). `MarkdownPre` hands it a fence whose info string is the word `table`, with the code block it would otherwise draw as its fallback. It reads the block, asks nothing when it cannot be read, and asks the host for one page; the answer is checked against the schema it carries, and a table the host does not keep, a block its columns cannot answer, or a host that rejects draws the fallback. A header is a button that sets the reader's order and asks again from the first page, never touching the note; the pages ask again too, and a later answer replaces an earlier one only if it is the last asked. Values are drawn as text — a number formatted by `Intl.NumberFormat` from its digits, a date by `Intl.DateTimeFormat` in UTC, a boolean as `strings.yes` or `strings.no`, a list joined — and the total sits in a `tfoot` under its column. In edit mode a `table` block the author is not in is drawn by `Snippet`, as a diagram is, so the same component draws it.
- **The editor** (`src/edit/`, exported at `@memorysmithapp/markdown-renderer/edit`, [ADR-006](#adr-006-a-note-is-edited-as-its-bytes-drawn-as-the-page)) edits a note on the page that draws it. `NoteEditor` holds the note in a CodeMirror 6 `EditorView` whose document is the note's text and nothing else; the page is drawn over it. `analyze` (`src/edit/analyze.ts`, no React and no DOM) reads the text with the parser of the reading surface — `remark-parse` with `remark-gfm` at `singleTilde: false` and `remark-math`, the micromark extensions of `readingPlugins`, whose tree transforms are not run because they drop positions — and the notation it leaves as text by the patterns the reading surface uses (`CALLOUT_MARKER`, `breaksDollarRule`, `commentRegions`, `codeRegions`, the wikilink pattern, and `parameterReferences` on the source of each text node, outside an autolink and a comment), and answers each construct as ranges of the text: what it covers, its notation, its content. `livePage` (`src/edit/live.ts`) keeps that analysis in a state field, made again on every change, and builds the decorations from it and from the selection: while the author is elsewhere a construct's notation is hidden and its content styled, a block is replaced by a widget that draws it with the reading surface's own components (`Markdown`, `Transclusion`, KaTeX) in a React root of its own, under the host's `HostProvider` and a `BlockBoundary` that, when drawing it throws — a host function or a slot reading the host's context, which that root does not carry — logs the error and shows the block's lines in a `pre` under `strings.editor.blockFailed` (#90), and that tells CodeMirror, which reads it once when the decoration is made, the height it will be drawn at (#91): `src/edit/heights.ts` estimates it from its lines wrapped at the editor's width, a table's rows and a frontmatter's keys — two lines a property below the default theme's 560px breakpoint, where a value goes under its key — by `BlockMetrics`, the width, line height and character width of the text column, which `NoteEditor` measures in its parent before the editor exists and a view plugin reads again when the geometry changes, and remembers in a map of at most 2000 entries, by width and content, the height a block's `ResizeObserver` measured, so a block made again — moved by an edit above it, or in the next edit of the note — starts at it; a block reads its estimate when it is made and compares by it, so whenever the decorations are built again — on any transaction that changes the selection, the text, the metrics or says `heightsLearned` — a block whose height was learned since is made again with it, CodeMirror reading the new one (#94); a block made again of the same kind — moved, its host given again under a new identity, its estimate learned, or its source changed — keeps its element through `updateDOM`, which draws it again in the same React root with the new widget's positions and the host as it is now, keyed by what it draws, so the same source keeps its tree and another replaces it on commit, the old one shown until then, and `drawing` tells the element's listeners and its measurement which widget it draws now; a block made anew starts with a `min-height` of the height it was last drawn at, released once what it draws is that tall or after two seconds, so no element is ever empty under the caret (#99); a rule, a formula by its rows and an image by the height it declares, which it is drawn at as the page draws it, estimate theirs too, and so does every line of text the editor shows (#94): CodeMirror lays a run of lines with no decoration out in a gap, estimated by the length of all its lines together — too tall on a wide column, too short on a narrow one — and a heading at the text's height, so `lineEstimates` puts at the start of every line with text a `LineEstimate`, a widget that draws nothing and whose `estimatedHeight` CodeMirror takes when it is taller than its own, the line's visible length — the notation the decorations hide taken away — wrapped at the width of the column by `lineHeightOf`: a heading by the metrics of its level and a line of code by those of a code line, both measured by `measureLines` from probes with the classes of the line, so what the theme gives them is what is measured, and text by the text's; an embed of a note, whose height no estimate can know, is drawn by `embedPremeasure` out of sight — `.cm-ms-premeasure`, hidden, `aria-hidden`, at the column's width and with the text's face and line — as the editor opens, which asks the host's `loadNote` for it a second time, and its height, once no skeleton is left, is remembered for the block and said with `heightsLearned`, or let go after 8 seconds, and a list's box is a checkbox that flips its one character; where the author is — the selection touches the construct, ends included, and the editor holds the focus — the notation is shown, dimmed, and a block shows its lines as source, a formula and a diagram with their drawing live below. An image — a Markdown image, drawn now with React like the blocks, and the embed of a file the notebook keeps, inline or on a line of its own — is drawn inside `ImageBlock` (`src/edit/blocks.tsx`, #98, #106), which offers, once an `img` is drawn inside it, its controls under the picture — a description field, editable for a Markdown image and read-only for an embed, the width in pixels or as a share of the page by a `select`, the lock between width and height, the height, and a button back to its own size — and a 24px handle at the picture's corner that drags it with pointer capture, keeping the proportion unless the lock is open or Shift is held. Both are placed by the picture's own box, which a layout effect and a `ResizeObserver` measure into `--edit-image-bottom` and `--edit-image-right` on the frame; under `(hover: none)` the controls stand in the flow. The lock starts as the notation is, locked for `|300` or none and open for `|300x180`, and decides what a field writes: the width alone, or both. The fields are text fields: each selects its value on focus, a click and a double click, writes on Enter or when left, and Escape drops what was typed; a value is checked against the range a reader sees — 16px to the wider of the text column and the picture's own width, 1% to 100% — and one outside it is refused with `aria-invalid` and `strings.editor.imageOutOfRange`, never brought into the range (#105). Each write goes through `resizeImage` or `describeImage` (`src/edit/image-size.ts`, no React), which read where the dimensions and the description are written — after the last pipe of a Markdown image's description when they are dimensions (`readImageAlt`), after the pipe of an embed, escaped or not — and replace, add or remove them alone, refuse dimensions the notation does not write, and never touch what an embed's pipe holds when it is not a dimension; the widget is found again by `posAtDOM`, its source checked before writing, and the image held on the screen for 600 ms after, against a jump of the page larger than 120px, which Chrome makes on a touch screen once the focused control is drawn again (#107). Nothing pressed on the controls reaches the widget's reveal-on-click: they carry `data-ms-control`, a press on them that is not on a field, a `select` or a button, or on the frame between the picture and them, has its default prevented — in Chromium that default put the editor's caret where the press fell, which drew the image's source — and the frame carries `data-ms-busy`, which the widget's `mousedown` honours as it does `data-ms-control`, while a control has the focus, while the handle is dragged and for 800 ms after a pointer or a touch on them. A click on a drawn block that shows its source puts the cursor where the text clicked is written in that source (#102): `sourceOffsetOf` (`src/edit/click-source.ts`, no React) takes the text node and offset the browser answers under the pointer and finds them in the block's source — the line of the drawn text, else up to 24 characters on either side of the pointer, at least three — at the occurrence the drawing shows, so a callout's body line is found after its `> `; text the source does not write as drawn, as a diagram's drawing or a note an embed draws, leaves the cursor at the end of the block's first line. The arrow keys enter a block rather than skip it. The blocks with controls of their own (`src/edit/blocks.tsx`) write through the same text: a callout's type and folding rewrite its marker, a table (`src/edit/table.ts`) is edited cell by cell where it stands, a Tab past its last cell adding a row, and grows or loses rows and columns and aligns a column from controls that keep the focus where it is, so each first commits the cell being edited, composing its text and the control's change into one, and acts on the cell the author was in, kept per editor across the table being drawn again, each by changes to exactly the bytes it names, and the frontmatter (`src/edit/frontmatter.ts`) is a form whose every field rewrites the lines of its one entry in the form it was written in, a boolean chosen as the reader's `yes` or `no` that reading draws and written back in the author's words (`true`/`false` or `yes`/`no`, in their case). Each property's key holds the property: `TypeChoice`, a transparent `select` laid over the icon of its type and the chevron after it that says it is a menu, then the button that removes it, always shown, standing in one column whatever the name's length, then its name; its value holds the value, a list with a + after its field. A new property is made of the type the author picks, written as the notation of an empty value — `key:`, `key: []`, `key: false`, or today's date — and `retype` gives an existing one another type, a list joined at commas as text, a text split at its commas as a list, any other value the new type's empty one; and an entry written as a list with no items, which `readProperties` reads as empty, is a list to the form. The field to focus once the form is drawn again — a new property's value, or a list's next item while the author types with Enter, a comma or Backspace — is kept per editor and focused once the widget is in the document. The toolbar and the shortcuts are commands over the selection (`src/edit/commands.ts`): delimiters written or taken away, the prefix of each line — a list's marker written on a blank line alone to start one, and a cursor between a line's start and its new marker moved after it —, a block on lines of its own, a footnote's reference and its definition, a comment. After `[[` the host's `suggest` is asked for names. A fenced code block's opening line carries `LanguageControl` at its top right: a button saying its language and a combobox that searches every grammar of `prism-grammars.ts` by its name, its identifier or an alias, best match first, with plain text and a Mermaid diagram first; choosing rewrites the first word of the fence's info string and nothing else, and a code block the toolbar or the menu inserts opens it, its search focused. A view plugin fetches the grammar of every block that names one not registered yet and draws the page again once it arrives. A right-click on the text opens `ContextMenu`, a `role="menu"` at the pointer — the cursor moved there first unless the click fell in the selection — with Edit's cut, copy and paste through the clipboard first (#110), then the toolbar's own commands — Format when there is a selection, and Insert — each with its shortcut, the focus on the first entry that runs; Shift+F10 and the context-menu key open it at the cursor. It stays inside the window, takes the arrow keys, Home, End and Escape, and closes on a click outside, a scroll after the one its click may cause, or an entry run. Shift, a field of a drawn block (`data-ms-control`) and a note the editor cannot change keep the browser's menu. The toolbar's paperclip opens `AttachDialog` (`src/edit/AttachDialog.tsx`), a `<dialog>` whose ways in are tabs: *From the computer*, where the host gives `attach` — files chosen, each with the name and the description the author edits and its type and size read from it; *From the notebook*, where the host gives `files` — its list, searched by name or description, an image previewed; and *From the web*, always — an address that must be `https:` or `http:`, its spaces written `%20`, and a name, written `![name](address)` with the name's brackets escaped. A file chosen, pasted or dropped on the text is handed to `attach` in turn and embedded as `![[name]]`, the name the host answered, on a line of its own at the cursor — at the drop's position for a drop — while the paperclip turns and, when the host could not keep one, says so for a moment and writes nothing for it; a file of the notebook is embedded the same way. Each file is handed `progress` (#88): the step it reports becomes the paperclip's title and the text of a live region beside it, followed by how many files wait behind it, and its `fraction`, kept between 0 and 1, an `.edit-attach-progress` `role="progressbar"` under the paperclip that fills by `--edit-attach-fraction`; a step reported after its file settled, or by a run of attaching a later one replaced, is dropped. A rejection `isAttachRefusal` recognises leaves its message as the paperclip's title with no timeout, until the paperclip is clicked, when the dialog says it at its top; any other rejection keeps `attachFailed` for a moment, as before. Closing the dialog without putting anything in the note gives the focus back to the paperclip. The editor splits its text on any line break and writes the note back with the one it was written with, so a block or a paste written with `\n` is CRLF in a CRLF note; a note that mixes them opens read-only. Every change reaches the host whole through `onChange`, and `useEditSaves` (`src/edit/saves.ts`) follows what the host answers as `useTaskSaves` does for a tick: a thenable puts the status before the switch at *Saving…*, then *Saved* or *Not saved* with a retry that hands the latest text again, a count keeping only the latest change's outcome; anything else leaves it empty. A host may say why (#86): a promise that resolves with a `SaveOutcome` puts the status in *Alert*, one rejected with a `SaveRefusal` in *Not saved* without the retry — both a `SaveNotice`, a title, a message and its actions, each a label and a `run`, recognised by `isSaveNotice` by shape, so any other value resolves or rejects as before. The status's icon is then a button named by the notice's title that opens `SaveNoticeDialog`, a `<dialog>` shown with `showModal`, its first action focused, which opens by itself as a notice with actions arrives (#101) and closes only on `cancel` or its ×, the focus back on the button and the state kept, or when an action is chosen: the action's answer is followed like a change's save and takes the place of the latest one in the count — a promise is *Saving…* and then *Saved*, a new alert or a new refusal, anything else *Saved* — and the focus goes back to the text. While the status is *Not saved* with a notice that has actions, `NoteEditor` makes the state `readOnly` and leaves the view editable, so the caret moves and the blocks' controls are disabled; a `keydown` that would write — a character, Enter, Backspace, Delete or Tab, without Ctrl, Meta or Alt — opens the dialog again, and the button's name adds `strings.editor.chooseToEdit`. A change the host makes to the note is taken in as the change it is, prefix and suffix kept, unless it is a text the editor handed and the host had not given back yet: a host that passes the note again once it saved it gives back texts the author has since moved past, and those are dropped, never applied. The toolbar's first button gives back the note as edit mode opened it, kept with `\n` for its breaks, as the one change from the common prefix to the common suffix, which Undo reverses and the host receives like any other. Beside the switch, in both modes, `NoteActions` (`src/NoteActions.tsx`, outside the editor, so a note that is only read offers it without loading it) draws Show Markdown and Copy Markdown: the first opens `SourceDialog`, a `<dialog>` shown with `showModal` (the `open` attribute where there is none), holding the note's bytes in a `pre` — the `markdown` the host gave in view mode, the text last handed to `onChange` in edit mode, which `NoteBody` keeps — with a copy through the clipboard; it closes on `cancel`, on its button or on a click on the dialog itself, which has no padding, so a click there is outside its frame, and gives the focus back to its button once it is closed. Copy Markdown puts the same bytes on the clipboard, shows a check for a moment and says so in a live region. Each of these buttons, the switch and the dialog's Copy draw their face through `ButtonFace` — the icon, then the word in a `.note-button-word` unless `buttons` is `icon` — and carry `data-buttons`; the word is the `aria-label` unless it is always drawn (#96). A `responsive` one measures its container: `NoteView`'s root, `.edit-bar` in edit mode and the dialog, each marked `has-responsive-buttons` and given `container-type: inline-size` — never the editor's root, whose containment would hold the right-click menu, fixed to the window. A container query cannot read a custom property, so `structure.css` computes a switch from the container's width, `clamp(0px, (100cqi - var(--markdown-button-words-from, 560px)) * 1000, 1px)`, 0px below the threshold and 1px from it on, and multiplies the word's `max-width`, the space before it and, in the default theme, the button's padding by it. `NoteBody` draws them with the switch in one `.note-corner`, floated at the top right in view mode and `position: sticky` at `top: 0`, so it stays in view while the note scrolls and the text flows around the place it takes at the top (#97), and alone there for a note that is not `editable` (#87), unless `actions` is `false`; the root carries `has-note-corner` when the group is drawn and `has-mode-switch` when it holds the switch; `NoteEditor` used alone draws them where the switch would be. The toolbar's box, in a sticky `.edit-bar`, ends at its top right with `.edit-corner`: the save's status — an icon in a slot of one size, a failed save's icon the button that tries again, so the toolbar never moves as the author types, its word the title and the whole status, why the note stays in edit included, in a live region — then the switch. The box grows out of that corner: a layout effect measures it from the toolbar's top right edge into `--edit-corner-width` and `--edit-corner-height`, where the clip of `markdown-toolbar-grow` starts and that of `markdown-toolbar-shrink` ends. Going back to reading is asked of the editor through `leaving`: it waits while a save is in flight, answers `onLeave(false)`, says why and shakes the corner once (`data-blocked`) when the last save failed, and otherwise sets `data-leaving` on the bar and answers `onLeave(true)` on the toolbar's `animationend` — at once when its computed `animation-name` is `none`, as under reduced motion or in a theme that does not fold it, and after 600 ms at the latest. `NoteBody` loads the editor with `lazy(() => import('./edit/NoteEditor.js'))` the first time a note is edited, behind the switch of #51: a note the host makes `editable` carries it at its top right, and the props below decide its mode.

### 1.2 The stylesheet of the reading surface

The stylesheet is three files. `theme-default.css` is the **default theme**: it carries every rule of MemorySmith's stylesheet that draws the body of a note — the reading surface's headings, lists, task items, blockquotes, footnotes, code and its frame, tables, callouts, embeds, wikilinks, pending and refused links, highlight tokens, Mermaid, the choice dialog and the embed skeleton — and none of the page around it. Every selector starts with `.markdown`, and a test parses the files to prove it. `structure.css` holds the few rules every theme needs whatever it looks like — `box-sizing`, the root positioned (`position: relative`) so that what is laid out of the flow, the live region of a ticked box among it, hangs from the note and never stretches a page that scrolls the note in a pane (#93), an image no wider than its column, a diagram's SVG fitted to it, the text kept for a screen reader, the place of an icon a theme draws as an element, where the lock of a task item and the switch sit, how the group at the top right — Show Markdown, Copy Markdown and the switch — and the editor's toolbar — its tools, each group drawing its separator on its left edge and overlapping the one before by that rule while the tools clip their own left edge, so a group that starts a wrapped row loses its separator and every row starts at the same place, then the corner with the save's status and that group, which takes the top row on a phone — the dialog of the note's Markdown, whose text alone scrolls, and the drawn blocks are laid out, a table's cell keeping a size of its own so an empty one can be clicked, a drawn block holding its own margins (`display: flow-root`) so that the editor measures the height it takes — and reads no colour, face or metric. The default theme draws edit mode in the reading surface's own values: the same faces, sizes and colours, the notation the author is in dimmed, the editor's controls small and neutral, the toolbar growing out of the switch and shrinking back into it (`markdown-toolbar-grow`, `markdown-toolbar-shrink`, off under `prefers-reduced-motion`, as are the turning loader and the shake of a refusal). `styles.css` imports the two, structure first, and is what a host imports for the default theme or for a theme built on it; a theme that draws everything itself imports `structure.css` alone. What MemorySmith's page gave the note from the document (the text face, the colour, `box-sizing`, the colour of a link) is set on the root of the note instead.

`NoteBody` draws its root as `<div class="markdown markdown-theme-<name>" data-theme="light|dark">`: the class names the theme, and `data-theme` carries the scheme. The root stands where MemorySmith's page had the document: each run of text is a `.markdown` inside it, and an embed, a pending embed and the notice of remote images sit beside the runs, outside any `.markdown`. So the rules on `.markdown[data-theme]` give the root the body's line height (1.45) and a paragraph's own margins to the paragraphs that sit directly in it, and the rule that takes the top margin off a first child applies to the runs, not to the root. The stylesheet sets its values there, as private `--ms-*` properties read from public `--markdown-*` ones with MemorySmith's value as the fallback, once for the light scheme and once for the dark. **Every value a rule of the default theme reads is public**, metrics included: a theme's `properties` are written on the root as these custom properties, and a host or a theme's own CSS may set them on the root or on any ancestor; nothing overrides a selector. Left unset, each one is MemorySmith's value, so the default theme draws what MemorySmith draws; a test holds the list of `ThemeProperties` and the properties the stylesheet reads to the same set.

### 1.3 Themes

A **theme** (`src/theme.ts`) decides how a note looks, never what its notation means ([ADR-003](#adr-003-themes-are-objects-a-host-writes-at-three-levels)). It is an object a host writes and checks with `defineTheme` — a `name` that becomes the root's class, the `schemes` it draws in (both, unless it names one), `properties` for every scheme or per scheme, `icons` by callout kind, and `components` — and passes as `theme`. MemorySmith's look is `DEFAULT_THEME`, named `default`: the stylesheet with nothing set over it, and the only theme the package ships. A theme works at three levels:

1. **Properties.** `ThemeProperties` names every custom property of [§1.2](#12-the-stylesheet-of-the-reading-surface) in camel case (`textSoft` is `--markdown-text-soft`); `NoteBody` writes the theme's values for the scheme on the root's `style`.
2. **Its own CSS**, scoped by `.markdown-theme-<name>`, which reaches anything inside the note and nothing outside it. It may also set the `--markdown-*` properties.
3. **Slots**: React components a theme fills, each called with the notation already interpreted (`src/slots.tsx`, where each one, left empty, draws exactly the default theme's markup):

| Slot | Called with | Where |
|---|---|---|
| `callout` | `kind`, `fold` (`+`, `-` or `null`, from `remarkCallouts`'s `data-fold`), `title`, `icon`, `children` | `MarkdownDiv`, for the `div.callout` `remarkCallouts` builds; a callout marked `+` or `-` is `FoldingCallout`, a `details.callout` whose `summary.callout-title` — the title, or its type's word — opens and closes it, open at first for `+` (#83) |
| `calloutIcon` | `kind`, when `icons` has none for it; the icon is drawn in the title as `.callout-icon` and the stylesheet's mask is hidden | the callout's title |
| `table` | `align` of each column, read from the first row, and `children` | `MarkdownTable` |
| `codeBlock` | `language`, `code` as typed, `children` (the highlighted `<code>`), `copy` (the Copy button, which copies `code`) | `MarkdownPre`, for a fence other than a diagram |
| `inlineCode` | `children` | `MarkdownCode`, outside a block (`InBlock` tells them apart) |
| `heading` | `level`, `children`; the footnotes' heading is never one | `headings` |
| `blockquote` | `children`; a callout is never one | `MarkdownBlockquote` |
| `embed` | `state` (`ready`, `section-missing`, `loading`, `pending`), `target`, `anchor`, `caption`, `children` | `Transclusion` |
| `attachment` | `name`, `file` (what `fileOf` said, its addresses through the filter; the default card opens a `data:` one as the `blob:` of its bytes, a browser navigating no tab to `data:`), `shape` (`image`, `audio`, `video`, `card`), `kind`, `size`, `opens`, `width`, `height`, `percent` (#108), `title` (what a Markdown image that names the file wrote after its destination, or `null`; its description is then `file.description`, #104); drawn only for a host that gives `fileOf` | `KeptAttachment` |
| `footnotes` | `label`, `children` (the list) | `MarkdownSection`, for the section remark-rehype gathers |
| `taskBox` | `checked`, `enabled`, `toggle`, which reports the box's ordinal and does nothing when it is not enabled, `pending`, while the host saves a tick of it (`checked` is then the state being written and `enabled` is false), and `failed`, once a save of it failed; the lock and the notice are drawn beside the slot, as `.task-lock` and `.task-notice` | `TaskItem` |
| `wikilink` | `pending`, `children`, `link`, which draws a label as the host's link to the resolved address, the choice, or the pending marker | `MarkdownAnchor` |

**The frontmatter is the theme's to draw** ([ADR-004](#adr-004-the-frontmatter-is-content-and-the-theme-draws-it)). `readProperties` reads it as `SPEC.md` §6 does — scalars, inline and dash lists, one layer of quotes — and gives each entry the shape §6.3 decides: `list` (by the form written, even with one item), `date` (its `YYYY-MM-DD`), `boolean` (`true`, `false`, `yes`, `no`), `text` up to 40 characters, `prose` past them, or `empty`; `name` is taken apart, as the note's name when it is a single text value. A value that is a wikilink, quoted or not, is kept whole. The default theme draws what MemorySmith's note page draws above the body, in its markup and its rules (*observed* at `4b67c7e`, `NotePage.tsx` and `PropertyValue.tsx`): the name as the note's title, `h1.note-title`, always — *Unnamed note* (`strings.unnamedNote`, `.note-unnamed`) when it has none — and, when an entry has a value, a `details.properties-box`, open, under a rule, whose `summary` says `strings.properties` and folds it. The reserved keys come first in the specification's order, `aliases` then `tags`, then the rest as written; an empty value is not drawn. Each `.metadata-property` carries `data-property-type` — `list`, `date`, `checkbox` or `text` — which picks the icon its key wears; a list is `.prop-tag` chips, a boolean the reader's `yes` or `no`, a date `Intl`-formatted in `strings.locale` (`dateStyle: medium`, in UTC; a form it does not read stays as typed), and the typed value stays in the title of each. In a value, a wikilink, a Markdown link to the web and a bare web address are links, drawn through `MarkdownAnchor` as the body's are, so the address filter holds and the theme's `wikilink` slot draws them too; they add no edge. Under 560px a key takes its own line. A host that shows properties elsewhere gives a theme whose `properties` slot draws nothing.

What a slot is handed is the result of the pipeline of [§1.1](#11-the-renderer), never the source: the address filter, the refusal of raw HTML, wikilink resolution, the task ordinal and the footnote numbers are decided before it is called, and the tests of `test/themes.test.tsx` and `test/properties.test.tsx` fill every slot and prove that none of them undoes one. The slots and the properties are public API: changing a slot's props or removing a property is a breaking change.

Each fact has one home: an invariant is stated in `AGENTS.md` and its mechanism here; a rule is stated in `PRD.md` and enforced where §3 says.

### 2.1 Toolchain

- **pnpm**, pinned in `packageManager` and enabled through Corepack; the workspace links the packages to each other, so the renderer's tests read the specification's data from the package, not from a copy.
- **TypeScript 5.9**, strict, configured once in `tsconfig.base.json`. Each package type-checks its sources and tests with `tsconfig.json` and emits ESM and declarations into `dist/` with `tsconfig.build.json`; `dist/` is what `exports` names and what a consumer receives.
- **Vitest 3**, configured once in `vitest.config.ts`. Each package's `test` script runs its project from the root (`cd ../.. && vitest run --project <name>`), so the configuration is never repeated; the renderer's project runs in `jsdom`.
- The versions of the toolchain and of the renderer's libraries are those the main repository's frontend locks at the commit the renderer is extracted from, so that "draws the same" is not disturbed by an upgrade (*declared* in #1, decision 2; the versions *observed* in that repository's `pnpm-lock.yaml`).

## 3. Invariants and their mechanisms

*Instruction: one subsection per invariant of `AGENTS.md` §5, saying what enforces it, or that nothing does.*

### INV-01 The version has one home

The version lives in the `version` field of the root `package.json` and nowhere else; `CHANGELOG.md` records the versions that were cut.

**Mechanism:** check 1 of [`scripts/quality.mjs`](../scripts/quality.mjs), run by the workflow *Quality*: the root `package.json` has a SemVer `version`, and it is the latest released section of `CHANGELOG.md`; on the branch `release/vX.Y.Z` it may be ahead of it, bumping to it; before the first cut it may be `0.1.0` with no released section. Check 7 holds the packages to it: every package of the workspace has the root's `version`, and a package that is not `"private": true` declares public access ([§4, npm](#4-integrations)). That the version is written in no other file is held by the writing map and the owner's review.

### INV-02 CLAUDE.md is only the import

`.claude/CLAUDE.md` is the line `@../AGENTS.md` and nothing else, and no `CLAUDE.md` sits at the root. Claude Code expands an `@path` line into the contents of the file it names, so the instructions load in every session and sub-agent; a `CLAUDE.md` that only mentioned `AGENTS.md` in prose would leave reading it to the agent's judgement (*observed* in this repository's first session, which started with `AGENTS.md` in its context). The path resolves from the file that holds the import: inside `.claude/`, `@AGENTS.md` imports nothing, and the session starts with the file listed as loaded and the instructions absent, with no warning (*observed* in fresh sessions, memorysmithapp/memorysmithapp-template#24). A `CLAUDE.md` at the root would load as well, beside the one in `.claude/`.

**Mechanism:** check 3 of [`scripts/quality.mjs`](../scripts/quality.mjs), run by the workflow *Quality*: `.claude/CLAUDE.md` is byte for byte `@../AGENTS.md` and an optional newline, and no `CLAUDE.md` exists at the root. The check walks no worktree under `.claude/worktrees/`, each a full copy of the repository.

### INV-03 main changes only through a pull request

**Mechanism:** the repository ruleset `main` (*observed*, id `24930653`), active on the default branch, with no bypass actors:

- `deletion`: the branch cannot be deleted;
- `non_fast_forward`: no force push;
- `pull_request`: every change through a pull request, with 0 required approvals, merge, squash and rebase allowed;
- `required_status_checks`: the check `Quality` passes before a merge.

Nobody can bypass it, administrators included (`current_user_can_bypass: never`, *observed*). A ruleset is a setting of the repository, not a file, so a created repository does not receive it: **`scripts/setup-repo.sh`** creates it there, or brings it back to this definition when it drifted. The script defines the ruleset in its own source and compares, rule by rule, only the parameters it sets, so a parameter GitHub fills in by default does not count as drift. The owner's run on 2026-10-12 created the ruleset above (*observed*); that a second run changes nothing is **To confirm** in this repository.

### INV-04 Only the release workflow writes a tag

A version names one commit: the tag `vX.Y.Z` is written once, on the merged commit, and never moved or deleted ([`SDLC.md` §10](SDLC.md#10-release), [§11](SDLC.md#11-rollback)).

**Mechanism:** the workflow *Release* ([`.github/workflows/release.yml`](../.github/workflows/release.yml)), on every push to `main`. [`scripts/release.mjs`](../scripts/release.mjs) reads the version, releases nothing when the GitHub links at the foot of `CHANGELOG.md` do not all name `GITHUB_REPOSITORY`, releases nothing when its tag names an earlier commit of the merged history, refuses to go on when its tag names a commit outside that history, and releases only when `CHANGELOG.md` has a section for it and the tag does not exist yet; the workflow then writes the annotated tag on `GITHUB_SHA` and the Release with that section as its notes. That nobody writes a tag by hand is held by the limit of `AGENTS.md` §4: the ruleset `main` protects the branch, not tags.

The link condition exists because a repository created from `memorysmithapp-template`, as this one was, receives that repository's `CHANGELOG.md`, its released sections included, in an initial commit pushed to `main`: without it, *Release* would publish one of those versions there on creation. In this repository, *Release* ran on the initial commit and wrote no tag and no Release (*observed*). Check 6 of [`scripts/quality.mjs`](../scripts/quality.mjs) holds the other side: the foot links name the repository the check runs in, so a changelog whose links name another repository fails `Quality` instead of leaving *Release* to skip in silence; it failed on this repository's initial commit for that reason (*observed*).

### INV-05 The documents keep their form

`CHANGELOG.md` keeps the format of Keep a Changelog 1.1.0, every relative link and anchor resolves, and no document carries a version footer.

**Mechanism:** checks 2, 4 and 5 of [`scripts/quality.mjs`](../scripts/quality.mjs), run by the workflow *Quality*. Anchors are computed as GitHub computes them (lowercase, punctuation dropped, spaces as hyphens, `-1`, `-2`… for repeated headings), which is what keeps the links of `AGENTS.md` into this document from rotting silently. Code blocks and inline code are skipped, so a link or a footer quoted as code is not read as one. A footer is a line *starting* with "Last revised", "Last updated", "Revision date", "Internal document" and the like; the words inside a sentence are not one.

### The specification keeps its three files together

Not an invariant of `AGENTS.md`, a rule of `PRD.md` (RN-SPEC-001, RN-SPEC-002), enforced here because it is the property the specification package exists for.

**Mechanism:** [`packages/markdown-spec/tools/check-spec.mjs`](../packages/markdown-spec/tools/check-spec.mjs), the first half of the package's `test`, run by `pnpm test` and so by the workflow *Quality*. It validates `spec.json` against its schema with a validator that implements only the keywords the schema uses and fails on any other; refuses duplicated identifiers, a case naming an undeclared notation, a case that asserts nothing, a notebook without a resolution and the reverse, a `links` or `frontmatter` notation with no case, a notice declared twice, raised by no case, raised by a case without being declared, or listed differently in the table of `SPEC.md` §7.13 and in `spec.json`, and a section reference — in the data or in the prose of `SPEC.md` — with no heading; fails when `SPEC.md` is missing instead of skipping it; and fails when the `url` of `spec.json` is not `SPEC.md` at the tag `v<version>` of the package's `package.json`. Its tests (`test/check-spec.test.ts`) run it against a copy of the package carrying one deliberate defect each.

### The renderer proves every reading-surface entry

Not an invariant of `AGENTS.md`, a rule of `PRD.md` (RN-RENDER-011), enforced here because it is what makes the renderer an implementation of the specification rather than a component that happens to draw most of it.

**Mechanism:** `packages/markdown-renderer/test/reading-surface-conformance.test.tsx`, run by `pnpm test` and so by the workflow *Quality*, reads the entries from `@memorysmithapp/markdown-spec` — the workspace package, never a copy — and holds an expectation for every `reading-surface` entry that is not in `DELEGATED_TO_THE_BASE_PARSER`; it fails on an entry with no expectation, on an expectation with no entry, and when the asserted and the delegated sets do not together make exactly the entries. `conformance-coverage.test.ts` runs that file in its own process against a copy of the data with one fake entry, through `MARKDOWN_SPEC_FIXTURE`, and requires it to fail.

### The demonstration notebooks show the whole notation

Not an invariant of `AGENTS.md`, a rule of `PRD.md` (RN-DEMO-001), enforced here because the notebooks are the first thing to age when a notation changes, and they age while teaching the wrong version to the person learning it.

**Mechanism:** `playground/test/notebooks.test.ts`, run by `pnpm test`, ported from MemorySmith's own guard: every entry of `spec.json` not in `DELEGATED_TO_THE_BASE_PARSER` has a detector and appears in **each** notebook; neither notebook demonstrates a notation the specification does not declare (a query block, a templater expression, a handlebars placeholder, an inline field); the forms the specification does not describe that somebody reaches for first — `#subject`, `H~2~O` — are shown being ignored; every link lands but the ones each notebook declares pending on purpose; and the reserved keys are in en-US in both. `playground/test/every-note.test.tsx` draws every note, frontmatter included, in both schemes of the default theme and in every scheme of each example theme, and requires every embed to find its note and no error to be logged.

### The renderer draws what MemorySmith draws

Not an invariant of `AGENTS.md`, a rule of `PRD.md` (RN-RENDER-001), enforced here because it is the test that decides whether the renderer is the reading page.

**Mechanism:** `playground/compare/compare.mjs`, run by hand with `pnpm --filter playground compare` ([`AGENTS.md` §6](../AGENTS.md#6-verified-commands)); it does not run in *Quality*, because it needs a checkout of MemorySmith with its frontend installed, two dev servers and a browser, and takes minutes. It draws every note of the two demonstration notebooks twice, in light and dark, at a desktop (1280px) and a phone (390px) width, and compares the two images pixel by pixel with `pixelmatch`:

- **The reference is MemorySmith's own component, not its site.** The script checks out `memorysmithapp/memorysmithapp` at `4b67c7e` (into `playground/compare/.memorysmith`, or where `MEMORYSMITH_CHECKOUT` names), installs its frontend, and copies `reference/` into it, so every import of the reference page is MemorySmith's: its `WritableContent` in the `.content-pane` of the note page, its stylesheet and its i18n in English, under a `MemoryRouter`, a `QueryClient` and the notebook's `NotebookIdProvider`, in a wrapper with MemorySmith's `.app-main > *` `min-width: 0`, so a long line of code scrolls inside its block as it does in the application. Its API module is replaced, by an alias, with `reference/backend.ts`, which answers the structure, the names and aliases, the kept files, the notes and the link targets from the same notebook files. The production site would differ for reasons unrelated to rendering: its chrome, its data and its fonts.
- **The other side is the playground**, `?bare=1`: the same note drawn by `NoteBody` with the package's stylesheet, in a pane of MemorySmith's measure, at the same address, so a picture a note writes as `../assets/<name>` reaches the same file.
- Both pages load the same faces from Google Fonts, and each image is taken once the fonts, the diagrams, the embeds and the pictures are in. A pair matches when at most 0.2% of its pixels differ; a pair that differs past that fails the run unless it is listed in `DELIBERATE`, with its reason. Every pair and its difference are written to `playground/compare/out/`.

The comparison covers what the default theme draws above the body too: `reference/main.tsx` draws MemorySmith's own title and properties block above `WritableContent`, from the same bytes through MemorySmith's `noteNameOf`, `splitFrontmatter`, `orderedProperties` and `PropertyValue`, as `NotePage` does. Of the 56 pairs, 52 are identical, pixel for pixel, title and properties included, and 4 are listed in `DELIBERATE`: the four images of the one note whose footnote an embed separates from its reference (RN-RENDER-013) (*observed* on 2026-10-13). What the comparison cannot see — what a click does — is held by the renderer's tests, and the differences the renderer has on purpose are behaviour, listed in `PRD.md` (RN-RENDER-009, RN-RENDER-012, RN-RENDER-013).

The npm organisation `memorysmithapp` exists since 2026-10-12, which reserves the scope, and is on the **free plan, which publishes public packages only**; a private package would need the paid Teams plan (*declared* by the owner in #1). No npm token exists (*declared*). Therefore, in the `package.json` of every repository of the organisation:

- **A package published under `@memorysmithapp` declares `"publishConfig": { "access": "public" }`.** npm publishes a scoped package as *restricted* by default, and on the free plan that publish fails with `402 Payment Required`; written in `package.json`, the access does not depend on somebody remembering `--access public`.
- **A package never meant to be published declares `"private": true`**, which stops `npm publish` whatever the plan. The root `package.json` of this repository is one: it is never published.
- **Publishing from CI goes through npm *trusted publishing* from GitHub Actions (OIDC)**, with no stored token, set up by the repository that first publishes, in an issue of its own.

This repository is that repository. Its two packages are published by the workflow *Release* through `scripts/publish.mjs` ([`SDLC.md` §10](SDLC.md#10-release)): the job holds `id-token: write`, npm exchanges the workflow's OIDC token for the right to publish — npm 11.5.1 or later is required, and Node 24 carries it — and generates the provenance attestation itself, since the repository and the packages are public (*declared* by npm's documentation, read on 2026-10-12). Each package is packed with `pnpm pack`, which writes the renderer's `workspace:` range on the specification as a version, and the tarball is published with `npm publish`. What a package ships is its `files`: the built `.js` and `.d.ts` of `src/` (no source map, no test), its `README.md` and `LICENSE`, and for the specification the document, the data, the suite and the checker; `scripts/pack-check.mjs`, run by *Quality*, compares `npm pack --dry-run` with that list and fails on a file missing or extra, and on two files whose paths differ only in case.

## 5. Operation

*Instruction: what runs, where, with which permissions and secrets.*

**Quality** (`.github/workflows/quality.yml`) runs on every pull request and every push to `main`, with `contents: read` and no secret; it reads the branch from `GITHUB_HEAD_REF` or `GITHUB_REF_NAME` for check 1.

**Release** (`.github/workflows/release.yml`) runs on every push to `main`, reads the repository it runs in from `GITHUB_REPOSITORY`, one run at a time (`concurrency: release`), with `contents: write` for the workflow's own `GITHUB_TOKEN`, `id-token: write` for npm trusted publishing, and no stored secret: it pushes the tag with git, as `github-actions[bot]`, creates the Release with `gh`, and on a release — or a run again on its tagged commit — builds the packages and publishes them with `scripts/publish.mjs`. A tag pushed with that token starts no other workflow.

There is no deployable. `scripts/setup-repo.sh` runs on a person's machine, once when a repository is created and again whenever its settings drift, with the permissions of the administrator whose `gh` it uses; it needs no token of its own.

## 6. Architecture decision records

*Instruction: the decisions behind the architecture, one record each, in the format below.*

Each record has an identifier, never reused; its context, decision, rationale and consequences; its date, status and **origin**. A decision that changes keeps its old record, marked *Superseded by ADR-NNN*, and a new record states the new decision.

### ADR-001 The types of the data live beside the data

- **Context:** the data of the specification is JSON, and every consumer retyped it. The main repository did, in `contracts/src/markdown.ts`, and a hand-retyped response is the defect that file's history warns about: the copy compiles, and drifts from the data in silence (*observed* at `4b67c7e`).
- **Decision:** `@memorysmithapp/markdown-spec` ships the types of its own data in `src/types.ts`, and typed entry points (`spec`, `conformance`, `cases`) next to the raw JSON exports. A test compiles every notation and every case as a literal against the types, compiles values the schema refuses to prove the types refuse them, and type-checks a consumer against the emitted declarations.
- **Rationale:** the types change in the same commit as the data (RN-SPEC-001 already makes the data move with the document), and the compiler, not a reader, checks that they agree. Generating them from the schema was not chosen: the schema says nothing about a conformance case, whose semantics live in `tests/README.md`, and a generator would be one more tool for a few dozen lines.
- **Consequences:** what an implementation decides on top of the specification is not typed here. The two lists the main repository calls "ours and not the profile's" — the entries delegated to the base parser and the forms deliberately left silent — stay with their implementations: the first with the renderer, the second with the main repository.
- **Date:** 2026-10-12. **Status:** Accepted. **Origin:** declared by the owner in #5.

### ADR-002 How the renderer carries its heavy libraries

- **Context:** `mermaid`, `katex` and `refractor` are heavy, and a host may already carry some of them. MemorySmith's reading page imports Mermaid lazily, typesets with the KaTeX that `rehype-katex` brings, and takes the stylesheet from its own `katex` dependency (*observed* at `4b67c7e`).
- **Decision:** `refractor` and `hast-util-to-jsx-runtime` are dependencies; so is `mermaid`, imported only through `import('mermaid')` inside `MermaidDiagram`, so a bundler puts it in a chunk of its own that loads when a note holds a diagram. `rehype-katex` is a dependency and brings the KaTeX that typesets; `katex` is a **peer dependency**, because what the host needs from it is the stylesheet and its fonts (`katex/dist/katex.min.css`), which only the host can import into its page. The versions are the ones MemorySmith's frontend locks.
- **Rationale:** a dependency the renderer cannot draw without belongs to the renderer, and installing it is not the host's problem; Mermaid's weight is paid at load time, not at install time, and the dynamic import is what keeps it out of the initial bundle. KaTeX's stylesheet carries fonts a bundler has to resolve, which is the host's work.
- **Consequences:** a host imports `katex/dist/katex.min.css` beside the package's stylesheet. A test reads the built `dist/` and fails if any module imports `mermaid` statically.
- **Date:** 2026-10-12. **Status:** Accepted. **Origin:** decided in #8, as the issue asked.

### ADR-003 Themes are objects a host writes, at three levels

- **Context:** a host that is not MemorySmith wants a note to look like its own pages, and to build that look in its own project and ship it with it (#28). Until v0.2.0 the renderer opened its colours, faces and radii as custom properties and kept the metrics, the callout icons and the table treatment private, because they are what drawing a note the same as MemorySmith means.
- **Decision:** a theme is an object (`defineTheme`) passed as `theme`, at three levels a host mixes: properties written on the root as `--markdown-*`, now naming every value the default theme reads; its own CSS, scoped by the root class `markdown-theme-<name>`; and a closed set of slots, React components called with the notation already interpreted. MemorySmith's look is the theme `default`, built the same way, and the only theme the package ships; `light` and `dark` keep meaning it. The stylesheet is split into `structure.css` and `theme-default.css`, with `styles.css` the two together.
- **Rationale:** properties alone cover most of a look with no CSS; a scoped stylesheet covers what a property cannot name without the package growing one per wish; slots cover a different structure — a callout drawn as something else, an icon from the host's library — which no stylesheet can. Handing a slot the interpreted notation rather than the source keeps what a notation means in one place, so any note works under any theme and no theme can reopen a security boundary. Fonts are not loaded by a theme: a theme names faces and the host loads them, as for the default theme.
- **Consequences:** the default theme's guarantee — the same drawing as MemorySmith — holds for the default theme only; the comparison tests it with no theme. Every property and slot is public API, so a change to one is breaking. Example themes live in the playground and are never published, so they can change freely.
- **Date:** 2026-10-13. **Status:** Accepted. **Origin:** declared by the owner in #28.

### ADR-004 The frontmatter is content, and the theme draws it

- **Context:** decision 4 of #1, carried by RN-RENDER-003, kept the frontmatter off the page: MemorySmith shows it as properties around the body, so the component drew the body alone. A host that is not MemorySmith then showed no properties at all unless it built them, and what the author wrote about a note was lost (#29).
- **Decision:** `NoteBody` reads the frontmatter (`readProperties`, by the shapes of `SPEC.md` §6.3) and hands it to the theme's `properties` slot, which decides how and whether to draw it. The default theme draws `name` as the note's title and every other entry by its shape. A wikilink in a value is drawn as a link the host resolved. A host that shows properties elsewhere gives a theme whose slot draws nothing.
- **Rationale:** the frontmatter is content, and the renderer's job is to draw a note, not only its body. Leaving whether and how to the theme keeps one place for the decision — no prop to turn it off beside the theme that draws it — and lets MemorySmith keep its page. A value's wikilink is drawn as a link because a reader expects it to be one; resolving it through the body's anchor keeps the address filter and the host's resolution in one place, and the specification's indexing is unchanged, so it adds no edge.
- **Consequences:** a note with frontmatter draws more than it did in v0.1, so a host that already drew its properties draws them twice until it turns the slot off. The default theme draws the title and the properties as MemorySmith's note page does (#30), and the comparison covers them. `splitFrontmatter` stays, for a host that reads the values MemorySmith does.
- **Date:** 2026-10-13. **Status:** Accepted; it supersedes decision 4 of #1 for the frontmatter, and leaves the rest of it — the source is never rewritten — standing. **Origin:** declared by the owner in #29.

### ADR-005 The notices live in the renderer, on a subpath without React

- **Context:** a host wants to hand the packages a note and hear where it will not be drawn as it was typed, from an editor and from a server or a tool with no DOM and no React (#35). There is no invalid note (`SPEC.md` §6.4), so whatever answers must report and never refuse. The reading of the notation — the parser, its plugins and their order — is the renderer's, and the specification package is data.
- **Decision:** `diagnose` lives in `@memorysmithapp/markdown-renderer`, exported at the subpath `./diagnose`, and reads through `readingPlugins`, moved out of `Markdown.tsx` into `reading.ts` so that nothing the subpath imports reaches React. It is asynchronous, because Mermaid reads a diagram asynchronously, and loads Mermaid only for a note that holds one. The codes are the specification's: `SPEC.md` §7.13 lists them, `spec.json` carries them as `notices`, each has a conformance case, and the renderer's `NOTICES` is held equal to them by a test.
- **Rationale:** one parser means a notice never disagrees with the page; a second reader in the specification package would be the drift ADR-001 exists to prevent, and would make a package of data carry a parser. A subpath costs nothing to a host that only draws. Declaring the codes in the specification lets another implementation report the same notices and prove it on the same suite.
- **Consequences:** a notice is what this renderer draws, so it reads comments as the page does: taken out before the parser, so nothing a comment holds raises one. `katex` and `mermaid` are reached by the subpath as they are by the component. A new notice is a change to `SPEC.md`, `spec.json`, the suite and `NOTICES` in one commit.
- **Date:** 2026-10-14. **Status:** Accepted. **Origin:** decided by the owner in #35, option 1.

### ADR-006 A note is edited as its bytes, drawn as the page

- **Context:** the renderer was taken out of MemorySmith so it could grow beyond drawing a note: the author should edit on the page the reader sees, WYSIWYG, in the notation of `SPEC.md` (#48). A note is its Markdown, kept byte for byte by MemorySmith, git and every other reader, so an editor that normalises — reorders a frontmatter, rewrites a list's marker, re-spaces a table, drops a comment or a construct it does not know — hands the notebook a file nobody typed. Three models were weighed (#49): a rich-text document (ProseMirror, Lexical) serialised back to Markdown, which re-writes the whole note and keeps the bytes only by carrying source positions on every node; the text itself drawn live with decorations (CodeMirror 6, as Obsidian's live preview does); and the renderer's drawing made editable block by block.
- **Decision:** the model is the text. `NoteEditor` is a CodeMirror 6 editor whose document is the note, and the page is decorations over it, built from the analysis of the reading surface's own parser and drawn, block by block, by the reading surface's own components; what the author is in is shown as its notation, and everything else as the page. Forms — a table's cells, the properties, a callout's type — write changes to exactly the bytes they name. The editor is on its own subpath, `./edit`, and `NoteBody` loads it with a dynamic import the first time a note is edited.
- **Rationale:** with the text as the model, a byte the author did not touch cannot change, whatever the note holds, and a construct the editor does not draw is still there to edit as source; no serialiser has to be proved round-trip for every notation. Reading with the reading surface's parser means the editor draws a construct where the page draws one, never by a second grammar. Drawing blocks with the page's components means a theme's look and slots hold in edit mode too. The per-block model was not chosen: inline marks and links could only be edited as source inside a block, which is less WYSIWYG than decorations, for a similar cost. A rich-text model was not chosen for the cost of byte fidelity over every notation, which is the rule this editor exists under. CodeMirror's packages are small, maintained, and already split by concern; the dynamic import keeps them out of a host that only draws.
- **Consequences:** a paragraph keeps the line breaks its author wrote, so in edit mode it wraps at them, where the page reflows it. A parse of a note is a few milliseconds (about 5 ms for the largest demonstration note, 28 ms for one ten times its size, *observed* on 2026-10-15), made again on every change. CodeMirror (`@codemirror/state`, `view`, `commands`, `language`, `lang-markdown`, `autocomplete`) is a dependency of the renderer, pinned. A drawn block's height is measured by CodeMirror, so a drawn block holds its own margins. jsdom lays nothing out, so the tests answer CodeMirror's measurements with zero and the playground is where edit mode is looked at.
- **Date:** 2026-10-15. **Status:** Accepted. **Origin:** decided in #49 on the owner's go-ahead for #48.

### ADR-007 The root holds only what a tool looks for there

- **Context:** every document sat at the root beside `package.json`, the lockfile, the workspace files and the dotfiles, pushing `packages/`, `playground/` and `notebooks/` down the listing a developer opens first. Only some of these files have a reason to be there: GitHub renders `README.md` and detects `LICENSE` only at the root, the agents that read `AGENTS.md` look for it there, and `CHANGELOG.md` is there by Keep a Changelog's convention and because the scripts read it there. Claude Code also loads `.claude/CLAUDE.md` (*observed* in fresh sessions, memorysmithapp/memorysmithapp-template#24). The template this repository was created from moved its documents in its v0.3.0, and its own ADR-004 leaves following it to each repository (#124).
- **Decision:** the root holds only what a tool or a convention looks for there. `PRD.md`, `ARCHITECTURE.md` and `SDLC.md` live in `docs/`. `CLAUDE.md` lives in `.claude/` as the single line `@../AGENTS.md`, and none sits at the root.
- **Rationale:** the root lists what a person or a tool opens first, and nothing looks for the three documents there. An `@` import resolves from the file that holds it, so the line in `.claude/` names the parent directory.
- **Consequences:** documents in `docs/` link to the root through `../`. `.claude/` is tracked, so `.gitignore` keeps out what Claude Code writes there for one person: `settings.local.json` and `worktrees/`. Prose keeps naming a document by its file name (`SDLC.md` §2); only a link carries its path. A published README links to a document by its URL on GitHub, which now carries `docs/`; a version already on npm keeps its old link until the next release. [INV-02](#inv-02-claudemd-is-only-the-import) checks the new line and the absence of a root `CLAUDE.md`.
- **Date:** 2026-10-17. **Status:** Accepted. **Origin:** #124, following memorysmithapp/memorysmithapp-template#24.

### ADR-008 The query language is read here, ported from MemorySmith's search

- **Context:** a `table` block filters a table of the notebook with `where`, in the language of MemorySmith's search, and a block whose filter cannot be answered is drawn as what is wrong with it and reported by `diagnose` (#136, #137). The renderer fetches nothing, so it cannot ask MemorySmith whether a filter reads, and the search's parser lives in MemorySmith's backend, which no package publishes. The language had been specified only for dates (`SPEC.md` §6.7, §6.8).
- **Decision:** `SPEC.md` §6.9 declares the whole language, with MemorySmith's search as its source, and `src/table-block.ts` reads it with a port of `SearchQuery.ts`: the tokenizer, the precedence, the folding and the errors, at the commit the comparison runs against. What the specification adds for a table — a field is a column, an interval compares a number, an inverted range is judged by the kind of its column, a phrase is text whatever it holds — is written in the port, and the conformance suite carries a case for each.
- **Rationale:** the page and `diagnose` must agree with the search on what a filter means, and a specification that the renderer and the backend both implement, proved by one suite, is how the two readers of the notation are kept together already (ADR-005). Publishing MemorySmith's parser as a package would bind this repository to the product's backend, which RN-RENDER-002 keeps out.
- **Consequences:** the grammar has two implementations, MemorySmith's and this one, and the conformance cases of §6.9 are what holds them equal; a change to the language is a change to `SPEC.md`, the suite and both parsers. Where the port departs from `SearchQuery.ts` at `4b67c7e` — a range over a number, an inverted range judged by kind, a quoted `"a:b"` read as text, `""` an error — the departure is recorded on memorysmithapp/memorysmithapp#366.
- **Date:** 2026-10-29. **Status:** Accepted. **Origin:** decided by the owner in #137.
